# Scheduler implementation and evaluation

For the measured Qwen experiment, its public workloads, and its per-request deadline derivation, see the [live experiment guide](live-experiment.md).

ReServe asks whether changing which requests start during a traffic burst can bring higher-precision weights back sooner while preserving on-time service. The scheduler returns a list of waiting request IDs for the next iteration. The device owns cache allocation and the precision transition.

## Follow one iteration

1. Put every request whose arrival time has passed in the waiting queue. Arrivals continue during generation and weight transfers.
2. Account for one more decode token for each running request. A token is the unit of text generated by the model. Reserve enough block capacity for that step before admitting new prompts.
3. Give the scheduler the waiting requests, running requests and current device budgets. Check the per-batch token limit, free sequence slots, instantaneous KV capacity and public growth reserve for each candidate. KV is the key–value cache that stores information about earlier tokens.
4. Process new prompts in full during prefill, producing their first output token. Each previously running request produces one more token during decode. The reference engine charges a single mixed-batch time. At step completion it releases the complete cache of each finished request. One logical block contains the configured number of tokens, rounded up per request.
5. Reconsider admission at the next boundary. The restore controller records eligibility, copy start, copy completion and readiness. Readiness can occur while the server is idle.

The online observation contains request ID, arrival time, absolute deadline, prompt token count, generated count and live cache blocks. The replay engine owns the recorded output length. The offline scorer owns burst labels. Neither value enters a scheduling call.

## How the policies make a decision

| Variant | Admission and precision |
| --- | --- |
| `fixed_high` | Earliest feasible arrival first with a fixed high-precision cache budget. |
| `fixed_low` | The same queue rule with a fixed low-precision cache budget. |
| `pressure` | The same queue rule with the shared dynamic controller. |
| `time-based` | Dynamic controller and smallest estimated deadline slack first. |
| `drain` | Deadline-slack ranking with a pause on elective admissions while a return is pending. Running requests can finish and release memory. |
| `space-based` | Deadline-slack ranking with a forecast of live cache after a fixed number of generation steps. A candidate can enter if the projected batch fits the high-precision restore budget. |

The predictor learns output-length distributions from separate calibration requests. It groups prompt lengths into power-of-two ranges. Once a request has already produced 8 tokens, for example, it uses only comparable historical outputs longer than 8 tokens. It falls back to the pooled calibration data if its prompt bucket has no survivors. Outside all calibration support it conservatively treats the request as continuing until the public cap or the next forecast. The default service estimate uses the 80th percentile of the conditional remaining length.

For a waiting request, **slack** is its deadline minus the current time and estimated service time. The service estimate includes the entire prefill and the remaining decode steps. Smaller slack receives priority. The estimate is the time to run that request by itself at current precision. Future queueing is uncertain.

For a horizon of a chosen number of steps, each request contributes its probability of still running at that point multiplied by the blocks it would occupy then. Finishing releases the whole cache. The policy sums the contributions from the running batch, the candidates it has already selected, and the candidate under consideration. The default synthetic horizon is 12 steps. A queued long prompt with a short output may fit the forecast because it can finish within those 12 steps. It must still fit the actual admission budgets today.

Urgent work with at most one estimated decode step of slack can bypass drain and forecast preferences. Requests waiting at least `max_wait_s` rise to the front, oldest first. When an aged request needs room currently occupied by other work, all three policies that rank by slack pause admission of younger requests until capacity opens. Every policy applies the same hard limits. Forecast errors can change who waits.

## Device interface and reference model

Use `RecoveryAwareScheduler.schedule(waiting, running, state, service_seconds, policy)` at an iteration boundary. Supply `OnlineRequest` views and an `AdmissionState` snapshot from the device. It specifies current precision, restore intent, remaining sequence slots, available prefill tokens, immediately available blocks after protecting ongoing decodes, the remaining public growth reserve, the high-mode restore target, block size and output cap. The service callback returns estimated remaining seconds for a candidate and its predicted output length. The return value is a list of IDs. Daniel can connect measured timings and allocator observations at this boundary. The runtime verifies feasibility before execution.

The CPU fixture uses an aggregate, resizable cache pool. It keeps the sum of public maximum per-request allocations within the largest mode the run can use. This is conservative for short outputs and guarantees room for future decode growth. A request whose prompt or public bound exceeds the empty device's limits is rejected and counted. In a dynamic run, momentary allocations must fit the **current** mode. The high-mode restore target deducts staging space used by the weight copy.

The dynamic controller enters low precision when the wait queue reaches `down_queue`, the next decode step needs more than high capacity, or an idle high-mode device has a waiting prompt that needs low mode to fit. After the minimum low dwell and when the queue falls to `up_queue` or below, it can request a return. The higher threshold for entering low mode and the lower threshold for leaving it reduce repeated switching. The fixture copies weights when the next running step fits the safe restore target. Arrivals continue during the copy. Generation resumes after the copy completes. The CPU model uses an instantaneous downgrade and a serialized restore.

Mixed-step time is a per-mode fixed cost plus terms for prefill tokens, decoding requests and their combined context length. Both supplied configs identify the timing source as artificial. Calibrate these terms, capacities, transfer timing and overlap on the assigned GPU before making hardware claims. An external allocator can require individual regions to become physically reclaimable. The reference fixture assumes blocks are reclaimable when their last simulated step finishes.

## Metrics and denominators

| Field | Definition and interpretation |
| --- | --- |
| `deadline_goodput_rps` | Fully completed requests that met their end-to-end deadline divided by the common observation duration in seconds. The duration includes the fixed follow-up after arrivals stop. |
| `deadline_attainment` | The same on-time count divided by all offered arrivals. A late completion, rejection, queue timeout, capped output or unfinished request contributes zero to the numerator. |
| `p95_ttft_s`, `p99_ttft_s` | Time from scheduled arrival to the first generated token among requests with an observed first token. Queue time is included. The 95th percentile is the value at or below which roughly 95% of observations fall. |
| `p95_tbt_s`, `p99_tbt_s` | Percentiles of the individual gaps between consecutive output tokens for the same request, pooled over observed gaps. Longer outputs contribute more gaps. |
| `p95_e2e_s`, `p99_e2e_s` | Arrival to last token among fully completed requests, including late completions. Read alongside unsuccessful counts. |
| `by_output_length` | Offline grouping by the original output length. Each group reports offered, on-time, never-started, p95 queue time among started jobs, and p95 observed wait across all jobs. A request still waiting at cutoff contributes the time already observed. |
| `recovery_s` | Sustained high-precision readiness time minus the offline burst end. Negative values mean early recovery. The ready interval must last at least `sustain_s` before the next burst or observation cutoff. |
| `trigger_to_ready_s` | Time from the most recent controller restore request in the successful episode to readiness. Events separately record actual memory eligibility and weight transfer. |
| `low_mode_s`, `low_token_fraction` | Total time in low mode, and output tokens produced in low mode divided by all observed output tokens, including partial responses. Quality requires a separate text evaluation. |
| `scheduler_mean_us`, `scheduler_p95_us` | Host CPU time around each scheduling call, excluding device work, simulation and file I/O. Timing varies by machine and load. |
| `token_throughput_s` | All observed generated tokens divided by the common observation duration. Late and partial outputs contribute to token throughput. |

Each arrival has exactly one terminal classification. `ok` means the original requested output completed, including after its deadline. `length_limited` means the configured output cap stopped a longer response. `timed_out` means the optional queue timeout elapsed before admission. `unfinished` means observation ended before a terminal event. `rejected` records the hard guard that prevented admission.

An episode is `no_switch` if there was no relevant low-mode interval, `censored` if there was a downgrade but too little observed high-mode time to confirm recovery, or `recovered` with its signed time. Fixed modes are labeled separately. For repeated bursts the next burst start ends the current observation. A persistent backlog can cause a first downgrade during the follow-up. In that case the scorer includes the delayed downgrade.

## Reproduce the comparisons

From the repository root, install the analysis extra and give each run a new results directory.

```bash
python -m pip install -e '.[analysis,dev]'
python -m unittest discover -s tests -v
for seed in 41 42 43; do
  recovery-run --config configs/scheduler.yaml --seed "$seed" --output "results/burst-$seed"
done
python scripts/plot_replay.py results/burst-42 results/burst-41 results/burst-43 --output results/burst-figures
```

`--steady-control` spreads the identical requests evenly while preserving their deadline budgets. `--scenario mild` lowers burst intensity. `--scenario long-tail` increases the share and duration of long outputs. `--deadline-budget-s 0.4` exercises deadline misses. `--prediction-scale 0.5` and `1.5` shift the calibration lengths for all policies while preserving the evaluation workload. `--restore-s 0` removes simulated copy time. `--policy space-based` runs a single variant.

For real arrivals, use the published BurstGPT CSV from commit `d895a53bb7b8ec137d0d2fe203b335835a78c10a`. The reader filters ChatGPT conversation traffic, uses original seconds `[28800, 57600)` for calibration and `[126000, 126600)` for evaluation, retains equal-time order and multiplies elapsed arrival times by 0.002. Zero-output source failures are counted separately before replay. The scorer labels the contiguous time bins around the highest arrival rate above a configured multiple of the window mean. [BurstGPT dataset](https://github.com/HPMLL/BurstGPT/tree/d895a53bb7b8ec137d0d2fe203b335835a78c10a)

```bash
git clone https://github.com/HPMLL/BurstGPT.git ../BurstGPT
git -C ../BurstGPT checkout d895a53bb7b8ec137d0d2fe203b335835a78c10a
recovery-run --config configs/scheduler-burstgpt.yaml --burstgpt ../BurstGPT/data/BurstGPT_1.csv --output results/burstgpt
```

The root `run.json` records settings, source hashes, environment, Git revision, burst labels and timing provenance. `workload.jsonl` and `calibration.json` freeze the two inputs. Each policy has `events.jsonl`, `requests.csv` and `summary.json`. The plot script produces `occupancy.png`, `recovery_goodput.png` and `paired.csv`. The CSV includes each policy's differences from `time-based` on the same trace, and keeps rows for unrecovered episodes.

## Results with the supplied CPU fixtures

Each synthetic run with seed 42 below has 98 arrivals. The observation duration is eight seconds. With a 2.5-second deadline, all three dynamic variants that rank by slack completed all 98 requests on time.

| Seed 42 policy | Recovery with 2.5 s deadline | Recovery with 0.4 s deadline | On time with 0.4 s deadline | Goodput with 0.4 s deadline |
| --- | ---: | ---: | ---: | ---: |
| Time-based | 0.620 s | 0.620 s | 52 / 98 | 6.50 requests/s |
| Drain | 0.630 s | 0.635 s | 54 / 98 | 6.75 requests/s |
| Space-based | 0.648 s | 0.641 s | 54 / 98 | 6.75 requests/s |

Across seeds 41, 42 and 43, space-based admission returned later than time-based admission on all three default bursts. With the long-tail workload it returned later on seeds 41 and 42 and earlier on seed 43 (0.720 s versus 0.803 s). On the tighter 0.4-second deadline space-based admission served 65/78, 54/98 and 57/98 on time across those three seeds. Time-based admission served 72/78, 52/98 and 67/98. The forecast's benefit depends on the workload and deadline. These results provide a comparison to repeat after GPU calibration.

The historical BurstGPT run used the earlier fixed six-second budget. The current BurstGPT preset derives a target per request from the held-out length predictor and DistServe streaming targets. The historical run used 1,049 calibration requests and 27 eligible held-out arrivals. The source had 66 calibration failures and 3 evaluation failures. All 27 eligible arrivals met their deadline and the dynamic runs stayed in high precision. The window validates real-trace replay and contributes a no-switch observation.
